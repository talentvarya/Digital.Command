# Digital Command — API Integrations

Six integrations are live (Anthropic API since Phase 2, extended for campaign drafting in Phase 6 and the AI Assistant in Phase 7; Google Search Console + Analytics since Phase 3, gaining a token-revoke call in Phase 7; Buffer + YouTube since Phase 4; Google Custom Search since Phase 5); everything else below is planned. Neither Phase 6 nor Phase 7 adds a new live integration — see the Google Ads/Meta Marketing API rows below for why. This inventories what's coming and where the seam will be, per spec §13/§39's modularity requirement.

## Integrated

| Integration | Used for | Since | Notes |
|---|---|---|---|
| Anthropic API (`@anthropic-ai/sdk`) | 7-Day Planner caption/hashtag generation; report narratives (Phase 3); off-page opportunity assessment + outreach drafting (Phase 5); paid campaign brief drafting (Phase 6); the AI Assistant's tool-use conversations (Phase 7) | Phase 2 | Server-only `ANTHROPIC_API_KEY`, model `claude-haiku-4-5-20251001` (cost-appropriate for short high-volume text, per spec §30/§32's cost-control emphasis). `lib/ai/generate-content.ts`, `generate-report.ts`, `assess-opportunity.ts`, `draft-outreach.ts`, `prepare-campaign.ts`, `assistant-tools.ts`/`assistant-chat.ts`, sharing `lib/ai/client.ts`. A monthly per-org safety cap (`MONTHLY_AI_GENERATION_SAFETY_CAP`) guards captions (and, as of Phase 7, assistant-triggered regeneration) against unbounded spend — the other call sites still don't have one yet (see `SECURITY_AND_RLS.md`). Campaign-brief drafting is the one call site whose output is adjacent to real money — its prompt is explicitly instructed to give budget guidance as qualitative ranges only, never a number presented as authoritative (see `ARCHITECTURE.md`). Phase 7 also added real per-call cost tracking (`ai_usage_events`, `lib/ai/log-usage.ts`) across every one of these call sites, feeding the Cost/Profit Dashboard (spec §30) — the first time this app captures the Anthropic SDK's own `response.usage` field, previously fully discarded. |
| Google Search Console API | Real indexing/impressions/CTR/position data + keyword tracking | Phase 3 | Real OAuth (`lib/google/oauth.ts`), plain REST calls (`lib/google/search-console.ts`), no `googleapis` SDK. **Needs the user's own Google Cloud OAuth app** (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) — I cannot create this on their behalf. Sensitive-scope, so only Google accounts added as Test Users can connect until the app passes Google's verification review (open item §37.13) — a real, potentially days-to-weeks external timeline. Phase 7 added real token revocation (`revokeGoogleToken()`, a verified — not guessed — `POST` to `https://oauth2.googleapis.com/revoke`) for offboarding, covering all three services this OAuth app grants (Search Console, Analytics, YouTube). |
| Google Analytics Data API (GA4) | Sessions/users/conversions/top pages | Phase 3 | Same OAuth app and verification caveat as Search Console (`lib/google/analytics.ts`). |
| Buffer GraphQL API | Facebook/Instagram publishing (spec §13) | Phase 4 | **Not per-client OAuth** — Buffer's current API only supports a personal key tied to one Buffer login (verified directly against developers.buffer.com before building; the per-client-OAuth model the spec seems to assume isn't available as of 2026). `BUFFER_ACCESS_TOKEN` is VMG's own key; `lib/buffer/client.ts`. Each client's channel is added to VMG's one Buffer account on buffer.com, then linked to the right org from the admin panel (`buffer_channel_links`). Full reasoning in `ARCHITECTURE.md`. |
| YouTube Data API v3 | Video upload, metadata, scheduled publish | Phase 4 | Direct API (spec §13 explicitly names full YouTube management as a Buffer-insufficient case), reusing the Phase 3 Google OAuth app with a third `service` value. Multipart upload (`lib/youtube/client.ts`) — large videos may hit serverless limits depending on the still-open hosting choice (spec §37.3). |
| Google Custom Search JSON API | Unlinked brand-mention search (spec §9.2) | Phase 5 | Simple API-key auth, no OAuth, app-wide credential (`GOOGLE_CUSTOM_SEARCH_API_KEY`/`_ENGINE_ID`). Free tier 100 queries/day. `lib/google/custom-search.ts`. Chosen specifically because it needs no vendor sign-off (no recurring-cost commitment at these volumes) — unlike the backlink-index-class providers below. |

Revisit once the user has an eligible profile and wants to start that process.

## Design constraint carried into the schema

Spec §25's generic `api_connections` table now has two real, differently-shaped instances rather than one speculative catch-all: `google_connections` (per-org OAuth tokens, client-managed) and `buffer_channel_links` (one shared account's channel IDs, admin-managed) — the Phase 3 prediction that this would need reshaping for Phase 4's different credential shapes turned out right. `api_health_events` (spec §25) is still **not created** — each connection table's own `status` column covers today's need; a dedicated events/incident table (feeding spec §27's `Connection Health Center` — `Healthy`/`Warning`/`Reconnect Required`/`Error`/`Rate Limited`) is worth adding once there's enough connection volume to justify it.
